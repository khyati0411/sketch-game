## Context

ADR-001 planned a public deployment on Render's free tier. Before deploying, the owner decided against third-party hosting for the game. GitHub stays for code, pull requests, CI and the Pages dashboard. The game still needs a running Node process for Socket.IO, and multiplayer has to work with real people, not only browser tabs.

## Options considered

| Option | Pros | Cons |
|---|---|---|
| Owner's PC, local network (chosen) | No third party; no cold starts; low latency; anyone on the same Wi-Fi can join | Players must be on the same network; the game is only up while the PC runs it; Windows Firewall must allow port 3000 |
| Owner's PC, localhost only | Simplest | Multiplayer can only be tested with several windows on one machine |
| Render free tier (ADR-001) | Public URL | Third-party hosting, which the owner declined; cold starts |

## Decision

Run the single Node service (built client + Socket.IO) on the owner's PC with `npm run build && npm start`. The server listens on all interfaces on port 3000 (`PORT` overrides it) and prints a join URL for this PC (`http://localhost:3000`) and one per local network address (for example `http://192.168.1.20:3000`).

`render.yaml` and the keep-alive workflow are removed.

## Consequences

- No public live URL. The showcase is the GitHub repo, the Pages dashboard, and live demos.
- The first time the server starts, Windows may ask whether Node.js can accept connections on private networks. The owner allows it for private networks only.
- Rooms stay in memory, and stopping the server ends all games, same as before.
- Non-functional targets (latency, 20 rooms × 8 players) are measured on the owner's PC and network.
- R3 (accounts, database) will need its own ADR. A local database fits this decision.
- `stories` will list the R1 stories that depend on hosting once they exist.
