## Context

US-005 requires guessers to see strokes while they are drawn, and every canvas to show the same picture when the turn ends. US-018 and US-019 require reconnecting players and late joiners to see the current drawing. US-021 sets the target: under 150 ms p95 from drawer to guessers with 8 players. The owner chose the server action log over a relay with image snapshots.

## Options considered

| Option | Pros | Cons |
|---|---|---|
| Server keeps the turn's action log (chosen) | Same picture everywhere by construction; late joiners and reconnects replay the log; undo is "remove the last action"; works when the drawer is offline | Server memory per turn; clients replay the log for undo |
| Relay strokes; drawer's browser sends a PNG snapshot to late joiners | Simple server | Depends on the drawer being online; snapshots can lag the live strokes; undo needs its own protocol |
| Send a bitmap every N ms | Trivially consistent | Heavy on the network; far from 150 ms with 8 players |

## Decision

**Coordinates.** All points use a logical canvas of 800 × 600, as integers. Each client scales to its screen size, so phones and laptops show the same picture.

**Tools and constants** (in `shared`):
- Palette of 16 colors, fixed for R1. The exact hex values are in ADR-007.
- Brush sizes 4, 10, 20 and 40 logical px.
- The eraser is a pen in the background color (white). The canvas background is always white.

**Actions in the log:**

| Action | Payload | Notes |
|---|---|---|
| `stroke` | `{ id, color, size, points: [x, y, ...] }` | Built from `draw:begin`, `draw:points` batches and `draw:end` |
| `fill` | `{ x, y, color }` | Flood fill from the point. Tolerance 48 per channel, so anti-aliased edges don't leave halos |
| `clear` | `{}` | Wipes the canvas; undo brings it back |
| `undo` | `{}` | Removes the last stroke, fill or clear still in effect. It is not stored as an action |

**Streaming.** While drawing, the client sends `draw:points` with the new points about every 30 ms (at most 33 ms between batches). The server checks that the sender is the current drawer and that the phase is drawing. It then appends the points to the open stroke and broadcasts them to the rest of the room. Socket.IO's ordered, reliable delivery keeps every client's log identical.

**Rendering.** Clients draw live points incrementally. On undo or `canvas:sync`, a client clears and replays the whole log, keeping a checkpoint bitmap every 50 actions so replays stay fast.

**Sync.** A player who joins or reconnects during a turn receives `canvas:sync` with the full log, including any stroke still being drawn, and then the live events.

**Limits.** A turn's log is capped at 50,000 points. After that, new strokes are refused and the drawer sees "Canvas is full: undo or clear to keep drawing". The log is emptied at the start of each turn.

## Consequences

- "Same picture everywhere" (US-005 AC4) is checked by comparing canvases at reduced resolution with a small pixel-difference threshold, because anti-aliasing can differ by a pixel between browsers.
- Server memory per room is bounded: 50,000 points × 2 integers, about 0.8 MB at most per active turn.
- The 30 ms batching uses about 30 ms of the 150 ms latency budget, which leaves plenty on a local network. US-021's automated test measures it end to end.
- Fill runs on each client against its own raster. The tolerance hides anti-aliasing differences, and US-008's test checks it in Chromium.
